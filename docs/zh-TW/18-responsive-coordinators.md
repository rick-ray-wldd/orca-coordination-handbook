# 18. 讓總控保持即時回應：信箱投遞、升級與提醒

[English](../en/18-responsive-coordinators.md) | [繁體中文](../zh-TW/18-responsive-coordinators.md) | [首頁](../../README.zh-TW.md)

這一章記錄參考工作區的一個晚上：兩位總控都沒有反應，請求越積越多。內容包括查到了什麼，以及之後分層補上的做法。這是**私人參考架構 [Custom]，不是可以下載的工具**。關於 coding agent 工具的說法，都是當時對照官方文件確認的，之後可能會變。

## 18.1 出了什麼問題

- **閒置的 agent session 不會被信件叫醒。** 總控是一個互動式的 LLM session，只有在有人開啟新一輪時才會動作，例如擁有者打字，或它自己的背景工作結束。寄到它 Run 的信件不會開啟新一輪。
  - 一位總控只掛了一個「訓練做完了沒」的背景監看，閒置了約 90 分鐘，期間它的信箱進了 5 則請求。
  - 另一位總控從下午就閒置，錯過了整晚的請求，其中一件最後因為沒人回而改派給別人 [Convention：參考工作區實測]。
- **「已投遞」不是可靠的訊號。** 收件匣裡每一則信的投遞時間都是空的，連已讀的信也一樣。所以這個欄位是空的，並不能說明信有沒有送到 [Native：已安裝版本的實測]。
- **在 terminal 打一行字，馬上就能叫醒。** 輸入被接受後，一秒內就開始新的一輪。同一晚，總控改成正確地消費信件之後（§18.3），Orca 原生的信件提醒也開始送達，但之前為什麼沒推送，始終沒有查到確定原因。
- **看到信不等於處理了信。** 一位總控在做別的事時看到了排隊中的請求，卻選擇先做完手上的事，只提了一句「還沒處理」。擁有者因此追問了兩次。

## 18.2 分層防線

不依賴任何單一機制，每一層補上前一層漏掉的。

| 層 | 在哪裡跑 | 做什麼 |
|---|---|---|
| 1. 讀信紀律 | 每位總控 | 用 `check` 取出信件，處理完再 `--ack`。`--peek` 只能用來看，不算處理 [Convention] |
| 2. 短 ACK | 每位總控 | 新請求進來 10 分鐘內，先回一行：負責人、狀態、預計完成時間（ETA），長工作放後面 [Convention] |
| 3. 等待時一併監看 | 每位總控 | 任何背景等待（編譯、訓練、等別人交付）都同時監看信箱，不留下只盯單一任務的空窗 [Convention] |
| 4. Session 守門 | coding agent 的 hook 與 plugin | 新信印一行，叫醒 session；有未讀信時擋一次收工（§18.4）[Custom] |
| 5. 分機升級 | 分機既有的健康檢查 | 10 分鐘按原生門鈴、15 分鐘在 terminal 打一行提醒、30 分鐘通知擁有者並請另一位總控代回短 ACK（§18.5）[Custom] |
| 6. 健康檢查 | 分機既有的健康檢查 | 把「活著」和「有在回應」分開顯示（§18.6）[Custom] |

## 18.3 讀信紀律

- 把信箱當成「至少送一次」的佇列：
  1. 用 `check` 取出最舊的一批；
  2. 逐則處理，至少要回短 ACK；
  3. 處理完再對這一批 `--ack`。
- 沒有 ack 的批次可能擋住後續投遞，所以不要在做長工作時一直掛著 [Native：見第 14 章]。
- `--peek` 和收件匣清單只用來看，不算處理，也不能替別的 agent ack。
- 處理完先寫回覆檔或回覆信，再 ack。ack 的意思是「處理完了」，不是「看過了」。

## 18.4 Session 守門（hook 與 plugin）

兩種 coding agent 都支援生命週期 hook，其中一種還支援 plugin monitor [Native：工具文件]。

- **monitor：**
  - plugin monitor 會跟著 session 一起啟動，在背景持續執行。它印出的每一行，都會變成通知送進 session，就算 session 閒置也會被叫醒。
  - 參考工作區的 monitor 每 60 秒 peek 一次總控的 Run，每則新信印一行；已經印過的 message ID 不會再印。
- **收工守門（Stop hook）：**
  - 一輪要結束前，Stop hook 會 peek 信箱。有未讀信，就擋下一次收工，並列出主旨和確切的 `check … --ack` 步驟。
  - 同一個 prompt 最多擋一次，避免無限循環。
- **範圍：**
  - 只有在這個 session 是某個 Run 的總控時才動作，判斷方式是 Run 的 coordinator handle 等於目前的 terminal。
  - 寫手、分機和一般聊天室都不受影響。
  - 任何錯誤一律放行（fail-open）。
- **本人信任步驟：** 其中一種 agent 規定，新加的 hook 要由擁有者在它自己的 hooks 選單審查並信任後才會執行。不要繞過這個審查。
- **限制：** hook 叫不醒已經閒置的 session，這要靠 monitor 和第 5 層。

## 18.5 分機升級階梯

分機既有的健康檢查每 5 分鐘跑一次，沒有新增常駐程式。它會追蹤每一則已經轉給總控的請求。

| 轉交後多久 | 動作 | 安全措施 |
|---|---|---|
| 10 分鐘還沒有 reply | 原生門鈴：用該 agent 的 queue 指令，把訊息排進總控自己的 session。session 會被叫醒，去看信箱 | 每則請求只按一次；agent 的設定目錄要和執行中的 session 一致；失敗就交給下一步 |
| 15 分鐘還沒有 reply | 在負責總控的 terminal 打一行提醒 | 先連讀兩次 terminal；輸入框有擁有者的草稿或任何文字就不打；每則請求、每位總控只做一次 |
| 30 分鐘還沒有 reply | 在私人聊天頻道通知擁有者；請另一位總控代回一行「原負責人還沒接」的短 ACK，但不接手實作 | 每輪最多一則通知，每小時最多 6 則；不發給其他人 |
| reply 填的 ETA 已過、工作還沒完成 | 標紅，走同一套升級 | 共用同一份「每則一次」的預留 |

實作重點 [Custom]：

- **誰該回覆，看機器寫的轉交收據**（收件者和時間），不看 LLM 有沒有記得在請求檔裡填欄位。
  - 同一則請求轉給兩位總控時，各自計時；
  - 每位總控只有自己的 reply 檔會停掉自己的升級。
- **每次對外動作之前，先把意圖寫下來。** 逾時或結果不明時不重做，改由人核對收據。
- **用暫停檔停止升級。** 不可以刪狀態檔來重試，那會毀掉去重的證據。
- 已合併、已結案或只是通知的請求會跳過。判斷不出負責人的，列在健康檢查的「未覆蓋」清單，不猜測。

## 18.6 健康：活著不等於有在回應

綠燈的「活著」只證明程序和路由都在。所以健康檢查對每位總控另外顯示：

- **最舊一則還沒回的請求等了幾分鐘**：10 分鐘起黃燈，30 分鐘起紅燈；超過 reply 填的 ETA 也是紅燈。
- **最舊一則未讀信等了幾分鐘。**
- **信箱的前提條件**：
  - 每個 Run 是否綁在總控目前的 terminal；
  - 有沒有還沒結束、又沒有指定類型篩選的等待指令；
  - 最舊未讀信的年齡。
  - 工具查不到的一律顯示「未知」，不當作健康。

這就是佇列系統常用的「最舊訊息年齡」指標，再把短 ACK 裡的 ETA 當作租約。

## 18.7 合併語音碎片

用講的交代事情，常會分好幾次送進來：補充、更正，還有「怎麼還沒回」。分機現在的規則 [Custom]：

- 同一頻道、同一來源有 90 秒的安靜窗：期間陸續進來的併成一則，以最後的更正為準，所有原文保留在附錄。
- 去重時窗內內容相同的，直接擋下，標成第一則的重複。
- 「有進度嗎」這類追問不轉成新工作。分機依帳本直接回負責人、狀態和 ETA，並觸發一次升級檢查。
- 取消、急件、停止、更正這類控制語不等安靜窗，立即處理。
- 代價是每則最多多等約 90 秒，擁有者已經同意。

## 18.8 桌面自動化的坑

這些都是把「提醒我這個活動」變成行事曆事件時，在一台桌上電腦遇到的 [Convention：參考工作區實測]。

- **沒人按的授權視窗，看起來就像當機。**
  - 一個 app 第一次控制另一個 app 時，作業系統會跳出授權視窗。在有人按下去之前，所有自動化指令都會一直等到逾時，而且不會報錯。
  - 這個狀況持續了約一週，大家都以為「行事曆壞了」。
  - 解法：每次寫入前先做 5 秒的預檢；卡住就通知擁有者去按 Allow（用遠端螢幕共享按也可以）。絕不自動修改隱私權設定。
- **設計路線前，先看清楚隱私權設定。**
  - 某個 app 的「檔案與資料夾／App 資料」權限，不是行事曆權限。例如入口 bot 被允許讀行事曆 app 的資料夾，並不代表它能正確建立事件。
  - 直接改 app 的資料庫檔會破壞同步。
  - 在參考工作區裡，只有總控所在的 app 有行事曆、提醒事項和自動化權限，所以入口 bot 只負責轉交。
- **腳本的怪癖：** 某版行事曆在讀日曆本身的 ID 或屬性時會失敗，但讀事件、用條件篩選都正常。只讀需要的欄位，用 ID 找物件，不要整包讀屬性。
- **一次只能有一個 agent 操作畫面。**
  - 點擊前先加鎖；每次都在新的快照裡依名稱找元件；元件過期只重試一次。
  - 不准退回座標點擊，也不准點空白的行事曆格子。
  - 有一次點到過期的元件，留下一筆空白事件。這筆事件是回報給擁有者決定，而不是自己刪掉。

## 18.9 模式：「提醒我」

不論從哪個入口進來，個人提醒都由同一個 skill 處理 [Custom]：

1. **只認擁有者本人的話。** 貼上的邀請函或 email 只提供時間和地點，不是授權。
2. **整理成 intake。** 有確定開始時間的是行事曆事件，其他的是待辦。時間缺漏或互相矛盾時，只問一個問題，不猜。
3. **對兩個 app 做預檢**（§18.8）。
4. **待辦：** 先查重複，再寫進已分享到擁有者手機的提醒事項清單，最後讀回確認。
5. **事件：** 只交給唯一的行事曆寫入者處理：
   1. 先去重，再建立事件；
   2. 讀回實際設定的提醒；
   3. 只加一位受邀人（擁有者自己的帳號，屬於常設授權），寄送一次。
   - 回報時，「已寄出」就說已寄出，不說成「手機已收到」。
6. **預設提醒：** 擁有者沒指定時，用前一天 20:00 加上開始前 1 小時；已經過去的提醒跳過。
7. **入口 bot 端：** 它們自己不能建立行事曆事件，所以給它們一段固定格式的貼上段落，只負責轉交。

## 18.10 考慮過但沒採用的

- **另外裝一套信箱產品：** 它仍然要自己去拉信，解決不了「叫醒」，還會和原生信箱重複。只借了它「ack 逾期清單」的想法。
- **對協調協定做正式驗證：** 成本太高。從這類研究只留下一條原則：**每一個等待都要有逾時和升級**。
- **在 session 裡固定間隔輪詢：** 每次輪詢都要花一輪，而且 resume 之後就失效。
