# 第 1 章　這份手冊是什麼

[English](../en/01-overview.md) | [繁體中文](../zh-TW/01-overview.md) | [Home](../../README.md)

這是一份**教學手冊與模板包**，說明一種「個人雙總控」的 Orca 工作方式：一位使用者（下文稱 User）同時讓兩個 AI 編碼代理擔任「總控」，由總控把事情分派給各專案底下的執行代理，再由另一位總控獨立審查，最後由 User 本人驗收與決定是否對外。

手冊從一個實際在用的個人部署整理而來。2026-10 版反映它最新的調整：改用原生受監督 worker、每位總控一個長駐 Run（第 14 章）、規則同步改走 mailbox、硬性安全邊界（5.7）、更嚴格的驗收用語（6.9），以及客戶訊息入口（第 15 章）。所有內容都經過人工重寫與去識別化：沒有私人姓名、帳號、專案名稱、路徑或 ID；公開 repo 的網址只用來識別本出版品。所有例子都是虛構的「網站A」「研究B」。

## 1.1 這個包有什麼、沒有什麼

| 有 | 沒有 |
|---|---|
| 架構與流程說明、名詞定義、派工與路由規則、審查與驗收規則 | 參考部署的私人工具（`assistant.py` 等**未隨附**；本 repo 另附模板複製與文件建置工具） |
| 可複製的匿名模板：AGENTS 規則、共同契約、路由設定、派工／回報／交接／審查／決策格式 | 任何真實設定檔、日誌、對話、資料庫或截圖 |
| 每項能力標明是「規約」「程式」還是「未知」 | 對 Orca 未來版本行為的保證 |
| 從零採用的步驟、排錯、分享前檢查清單 | 對外送件、付款、公開發布的授權 |

> **重要**：下載這個包之後，你**不會**得到一支能直接跑的 `assistant.py`。手冊裡提到的自製 CLI 只是用來說明「參考部署怎麼做」，介面摘要寫在第 3 章與附錄，讓你可以自己實作或改用純文件流程。Orca 本身的命令（`orca worktree ...`、`orca terminal ...`、`orca orchestration ...`）則是 Orca 原生功能，需要你自己安裝 Orca。

## 1.2 三種能力標記

整本手冊在描述每項能力時都會加上一個標記：

| 標記 | 意思 | 例子 |
|---|---|---|
| **〔規約〕** | 寫在規則文件裡、靠代理與人遵守；沒有程式會擋 | 「只有該領域的督導可以對聊天室送輸入」 |
| **〔程式〕** | 有程式實作會強制或自動執行；括號內註明怎麼核實的 | 「任務轉 done 必須附 evidence 與 reviewer」（自製 CLI 會拒絕） |
| **〔未知〕** | 本手冊作者沒有實際核實，或隨版本可能變動 | 手機版 App 的畫面細節 |

「程式」再細分兩種來源：

- **〔程式・原生〕**：Orca 本身提供，可用 `orca --help`、`orca <命令> --help`、`orca skills get <名稱>` 在你自己的機器上查到。本手冊核對的是 Orca CLI 1.4.220 版。
- **〔程式・自製〕**：參考部署自己寫的腳本提供。**本包沒有附這些腳本**，你要自己做才會有。

規約不等於強制。如果一條規則只寫在文件裡，代理忘了讀、讀了沒照做，系統不會阻止。這也是為什麼第 6 章強調證據與獨立審查。

## 1.3 誰適合讀

- 已經在用 Orca（或類似的多終端 AI 代理工作台），同時開很多聊天室，開始覺得亂的人。
- 想讓兩種不同的 AI 代理互相制衡（一個做、一個查），而不是全部交給同一個。
- 想把「AI 說做完了」和「我確認做完了」分開記錄的人。

## 1.5 用語約定

- **User**：使用者本人，唯一能做最終驗收與授權對外動作的人。
- **總控**：被 User 指定負責「收件、判斷、派工、追蹤、整理證據」的 AI 代理聊天室。本手冊的參考部署有兩位：一位 Claude Code、一位 Codex CLI，下文稱「總控 A」「總控 B」。哪一位是 A 或 B 不重要，重要的是兩者互為審查者。
- **writer（執行者）**：真正動手改檔案、寫內容的代理聊天室。
- **reviewer（審查者）**：不參與製作、只讀核對的一方。
- `HUB_ROOT`：放總控規則、路由、回報資料的個人工作區根目錄（範例路徑，不是真實路徑）。
- `PROJECT_ROOT`：某個專案的根目錄。
- `example.invalid`：所有範例網址使用的保留網域，不會連到任何真實網站。
- `T-EXAMPLE0001`、`S-EXAMPLE-A` 這類 ID 都是人造的。
