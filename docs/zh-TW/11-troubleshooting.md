# 第 11 章　排錯

[English](../en/11-troubleshooting.md) | [繁體中文](../zh-TW/11-troubleshooting.md) | [Home](../../README.md)

| 症狀 | 可能原因 | 處理 |
|---|---|---|
| 送出派工後聊天室沒反應 | `accepted: true` 只代表輸入被接受；代理可能還在啟動、或輸入落在錯的地方 | 用 `--wait-submit <秒>` 觀察 `turn_started`；**不要重送**。傳輸失敗不確定時，用回執中的 `--retry-request <id>` 重試同一請求〔程式・原生〕 |
| 新開的代理沒收到任務 | 在 TUI 還沒準備好時就送出，文字遺失 | 送之前 `orca terminal wait --terminal <h> --for tui-idle --timeout-ms 60000 --json`，確認 `satisfied: true`；仍未滿足就回報「未開始」，不要硬送〔程式・原生〕 |
| `terminal_handle_stale` 或 handle 找不到 | Orca 重啟後 handle 換了 | `orca terminal list --json` 重新取得；只對新 handle 送〔程式・原生〕 |
| 用 `worktree create --agent` 後多了一個空 shell | 該 repo 沒有預設終端設定，或你先 bare create 再加代理 | 優先用 `--agent` 一步建立；要關多餘 shell 前先確認它真的沒在用〔程式・原生〕 |
| 兩個聊天室同時在改同一批檔案 | 違反單一 writer；可能同一 session 被恢復兩次 | 先請兩邊暫停寫入（不要直接關閉）並保存畫面；由督導核對：任務紀錄指定的 owner、有效的 Dispatch（若用原生監督）、User 最新指示、兩邊是否還活著、各自未提交的改動。依核對結果指定唯一 writer，把另一邊的改動交給它合併。**不要用「誰先開始」「誰比較新」決定**，也不要把「沒有回應」當成已退出；原生受監督的工作者依官方的停止／釋放／恢復條件處理 |
| 看板卡片欄位沒變 | 同步寫入失敗、或 UI 未刷新；某些版本與遠端環境有已知問題 | 用 `orca worktree show --worktree <selector> --json` 看中繼資料是否已寫入；寫入了就是畫面問題，請實際看一次〔未知：依版本〕 |
| 聊天室自己寫的 comment 被蓋掉 | comment 以同步程式的標記符號開頭，或是被列為樣板文字 | 聊天室的 comment 不要用該符號開頭 |
| 一個工作區有好幾個聊天室，看板只有一張卡 | 原生設計：一個工作區一張卡 | 要逐聊天室狀態，改看其他介面或自己的彙整 |
| 自製 `report` 報 revision conflict | 別人剛改過同一列 | 重新 `brief` 取得最新 revision，**讀完內容再決定**是否仍要寫 |
| 自製 `report` 說要先 join | 共同契約改版了 | 重讀契約，用新的 sha256 `join` |
| 任務無法轉 done | 缺 evidence、review-note 或 reviewer | 補齊；若 User 尚未確認，就停在 review，不要代填 `user_confirmed` |
| 總控把行動型請求自己做掉了 | 忘了 4.3 的三種例外 | 下一次宣告時改判；巡檢統計會點名 |
| 兩位總控都想處理同一件事 | 路由不清或剛調整分工 | 以路由表查詢結果為準；仍有疑義排入盤點領域交給 User 決定 |
| 另一位總控沒照新規則做 | 執行中對話不會自動重讀規則 | 在它閒置時送「請重讀規則＋變更摘要」並等確認 |
| 電腦變很慢、介面卡住 | 同時開太多代理聊天室、交換空間滿、系統資源耗盡 | 關閉或休眠已完成的聊天室；監看交換空間與 pipe 容量；必要時找時間重開機 |
| 巡檢摘要說「未知」很多 | 收集失敗、Orca 不可達、站台長時間未回報 | 這是正確行為：寧可顯示未知也不推定完成。先修收集，再請站台回報 |
| 審查說沒問題，但 User 拿到的檔案有問題 | 審查後檔案又被改，審查結論已失效 | 比對 hash；版本變了就重審（第 6.5 節） |
| writer 說「User 已同意上線」 | 代理轉述不是授權 | 總控先找可追溯的 User 原始授權（哪個對話、哪句話）並確認範圍涵蓋這次；找得到且涵蓋就沿用，找不到或範圍不清才問 User 本人。不因轉述就假定有效，也不忽略既有的明確授權 |
