# 21. 專案維運：CTO、派工、巡檢、看板、雲端路徑與紀錄

[English](../en/21-project-operations.md) | [繁體中文](../zh-TW/21-project-operations.md) | [Home](../../README.zh-TW.md)

第 19、20 章說明了入口，以及誰的話算數。本章說明入口背後的事：每個專案一位 CTO、派工怎麼宣告和補充、每日巡檢、看板、雲端硬碟的放法，以及一定要留下的紀錄。這是**私人參考架構〔程式・自製〕，不是隨附工具**。標籤沿用第 1 章。原生命令對照過本機安裝的 Orca CLI 1.4.253 help；複製前請先查你自己的版本。

## 21.1 每個專案一位 CTO

**專案 CTO** 是負責一個專案的 Orca 總控聊天室。它有自己的 orchestration Run 當信箱，負責派這個專案的 writer、驗收它們的交付〔規約〕。第一位是一個合作專案的長駐督導，之後的 CTO 都照它的工作說明。

**成功的樣子：** 專案裡的每個問題都有人接，每個 writer 的交付都有人真的驗收，主總控只收到要擁有者決定、或 CTO 自己解決不了的事。

| | 專案 CTO |
|---|---|
| **負責** | 專案 bot 和 bot 對接員轉來的問題；拆成工作；派 writer；驗收；留證據；回報自己的 station；這個專案的技術與內部決定 |
| **不負責** | 別的專案（回「不是這個專案」，交回去）；批准任何對外的事 |
| **可以自己決定** | 回答進度、內部決定、開工單、派 writer（同時最多兩位）、驗收 |
| **要先經總控問擁有者** | 價格、範圍變大、新對象、寄信、發文、送件、上線、部署、公開分享。部署只由負責部署的那位總控執行 |
| **絕對不做（適用：CTO 與它的 writer）** | 付款；建帳號；輸入密碼或 token，或把它們放進指令或聊天；改系統或隱私設定；把真實客戶資料或個資放進 repo、log 或聊天；把 repo 公開。下載檔案前先問，寫明檔名、來源與大小 |

bot 轉來的話是 B 或 D 級（第 20 章），**不能擴大 CTO 的權限**。內容要求超出權限的，CTO 退回給擁有者。

**狀態放在哪。** 工單和狀態檔都放在總控的私人工作區，不放進專案 repo，因為專案 repo 可能是公開的。

**寄信紀律**〔規約〕：

- CTO 只有在這些情況才寄信給總控：要擁有者決定、自己判斷不了、writer 卡住而自己解不了、額度不足。
- 「writer 交件了」不寄。擁有者發現這類信件一多，注意力就被拉走。
- 每天晚上最多一封五行以內的摘要；沒有事就不寄。

**驗收就是要親眼看。** CTO 不只讀 writer 的回報：要自己看截圖和實際輸出，並用真實資料或真實環境測一次。全部用 mock 的測試不算數。沒看過的，就說沒看過。CTO 驗收完，也還不是擁有者的驗收（第 6 章）。

**CTO 開工步驟：**

1. 讀 CTO 工作說明、營運規則、專案對照表和這個專案自己的文件。
2. 只讀盤點：相關工作區、開著的聊天室、還沒驗收的交付、下一步。
3. 建自己的 Run（`orca orchestration run-create`），把 Run、自己的 terminal handle 和盤點結果寫進最多 20 行的狀態檔，並回報自己的 station。
4. 然後等。不寄信給總控報到，也不自己主動開工。

**上限與閒置：**

- 活躍的 CTO 有固定上限：參考部署是 5 位，加上那位合作專案督導。原本是 3 位，擁有者要求另外兩個專案也各設一位後才調高。
- **閒置 48 小時的 CTO 會回報可以收起來**，要用時再恢復。
- 不活躍專案的 bot 不設排程。每次按門鈴、每次轉交都吃 bot 的額度，所以工單能合併就合併。

**總控只督導，不親手寫。** 主總控只能親自做三種事：快速的唯讀回答、自己督導領域內的系統工作、擁有者明確說「你自己做」的事（第 4 章）。其他都要派出去，而且只能由該領域的督導派送。

## 21.2 派工：宣告、寫明限制、記錄

[第 4 章](04-dispatch-routing.md)的五種派工判斷，現在適用於每一個入口，包括 Slack 與 bot〔規約〕：

1. 動手前先判斷。一個依規則運作的分流工具會建議領域、候選專案與聊天室，以及選項；最後由總控決定〔程式・自製〕。
2. **回覆的第一行先宣告處理方式**：`判斷：<編號> <處理方式>｜<對象>｜<一句理由>`。擁有者可以直接改判。
3. 派工訊息必須包含：擁有者的原始需求與成功條件；可寫範圍與禁止事項（送件、付款、寄信、公開分享、建帳號）；能不能開新 terminal 或啟動其他 agent、最大併發數與額度上限；交付要附自測證據；完成後回報 writer 自己的 station。
4. **每一條限制都寫明適用對象**：writer、總控，或全部。例如「新增 terminal／agent＝0（含總控本人和總控的子代理）」，這樣就沒有任何 session 需要猜一條限制管的是誰。
5. **每次判斷都要記錄**：選項、對象與總控。對象可以是 terminal、路徑、bot 收件匣或接線員。每日巡檢會統計這些紀錄，並點名「行動型請求卻由總控自己做」的情況。

[分流範例](../../templates/zh-TW/triage.example.json)包含各選項、宣告格式、三種可以自己做的情況，以及派工訊息的必填項目。

## 21.3 派工後的補充指令

writer 開工後，後續指令不再走信箱。原因是實際遇過：寄到信箱給一位閒置 writer 的補充指令一直沒被讀，writer 就這樣閒置了 50 分鐘，因為信箱的信不會叫醒閒置的 terminal（第 18 章）。

- **補充指令和回覆直接送進 writer 的 terminal**〔規約〕，透過一支小包裝工具〔程式・自製〕。要在**兩分鐘內看到 writer 開始新的一輪，或文字明顯排進佇列**，才算送到；否則工具回報「未確認」，這則訊息就當作沒送到。每次嘗試都記進本機 log。
- `orca orchestration send` 只用在總控之間，以及 worker 的正式回報。
- **送出前，對象必須閒置、輸入列是空的。**

**草稿還是灰色建議？** 參考部署用的 coding agent 每一輪結束後，會在輸入列放一句灰色的「下一步建議」，要按 Tab 才會真的打上去。Orca 的 `terminal read --json` 會把它放進 `draft` 欄位，分不出兩者〔程式・原生：實測；1.4.253 的 help 寫明 `draft` 是只屬於介面的輸入框文字〕。擁有者確認過這條判斷規則：

| `orca terminal read --screen` 顯示 | `draft` 欄位 | 意思 | 怎麼做 |
|---|---|---|---|
| 只有提示符號，後面沒有字 | 有字 | 灰色建議 | 照常送；送出的文字會取代它 |
| 提示符號後面真的有字 | 有字 | 擁有者真正的草稿 | 不要送、不要清，問擁有者 |
| 看不清楚 | — | — | 問擁有者，不要猜 |

## 21.4 每日巡檢：一天三次，只讀

〔程式・自製〕

- **每天三個固定時間**（清晨、中午、深夜），排程工作巡檢整個工作區。
- **設計上就是只讀。** 事實由一般程式收集；摘要由一個較小的模型撰寫，而且**完全不給任何工具**，所以它不能修改任何東西。報告有行數上限。
- **看什麼：** 超過 72 小時的回報標為過期、三天內到期的期限標出來、統計派工判斷，並點名由總控自己做的行動型請求。
- **結果送到哪：** 系統通知頻道（兩個聊天 App 都會貼，只有其中一個會跳通知），以及一個常駐的「每日巡檢」任務，所以看板上也看得到。
- **開工或接手前，** 總控先讀最新一次巡檢。
- **另有健康檢查**，每 30 分鐘比對記憶體交換空間、pipe 容量、剩餘磁碟和 agent 程序數量的門檻；超過門檻才示警，冷卻三小時。這些門檻是在一次系統當機前剛好出現這些徵兆之後訂的。

## 21.5 用 Orca 看板顯示進度

參考部署停用了自己的 HTML 看板：在 App 內建瀏覽器裡開起來很慢，也不即時。進度改用 Orca 內建的 **Workspace board** 顯示〔程式・原生〕，由一個同步工作驅動〔程式・自製〕。

| 欄位 | 對擁有者的意思 | comment 開頭 |
|---|---|---|
| `todo` | 要你決定或提供，或還沒開始 | ◆等你／◆阻塞／◆收件 |
| `in-progress` | 有聊天室正在做 | ◆進行中 |
| `in-review` | 已交付，等你驗收 | ◆待驗收 |
| `completed` | 你確認完成 | 同步永遠不會自動移入，由你拖過去 |

- **兩種 comment。** 以 ◆ 開頭的是同步工作寫的：`標籤｜事項（另 N 項）｜下一步｜督導`。沒有 ◆ 的是該聊天室自己的檢查點，用 `orca worktree set --worktree <selector> --comment "<文字>"` 寫；同步只調整欄位，絕不覆蓋這種 comment。聊天室自己寫 comment 時不能用 ◆ 開頭。
- **同步**每 60 秒跑一次，只寫有變化的卡片。擁有者手動拖過的卡片會留在原處，直到它的實際狀態又改變。
- **限制**〔程式・原生：實測〕：一個工作區只有一張卡，不是每個聊天室一張；逐聊天室的狀態要看實驗功能 Agent Dashboard。官方手機 App 顯示 agent 狀態與檔案，但不顯示看板，所以參考部署另外產生一份手機打得開的純文字「今日」檔。因為已知問題，不用自訂欄位 id，只用預設四欄。

## 21.6 雲端硬碟：單一路徑規則

所有共用檔案都放在擁有者雲端硬碟裡的同一個根資料夾下；每則訊息、每份文件和工單都用**同一種地址寫法**指向檔案，絕不寫某台電腦的路徑〔規約〕：

```text
<根>/<組>/<專案>/<類型>/<YYYY-MM-DD_主題_說明_v版本.副檔名>
```

- **組**的編號和 Slack 頻道分組相同，另外加上「先讀」組、加密備份組和封存組。
- **類型只有四種**，第一次用到再建：*交付*（給別人或已定稿的成品）、*媒體*（影片、圖片、3D、素材）、*文件*（研究、規格、筆記、簡報）、*收據*（驗證證據、截圖、QA 報告）。
- **檔名：** 日期用系統時鐘取，不手打；同一份改版就加版本號，不覆蓋；不放內部案件代碼、工具名稱、金額或個資，因為分享時檔名看得到。

三個平台怎麼到同一個檔案：

| 平台 | 怎麼找 | 能做什麼 |
|---|---|---|
| Orca | 桌面同步用戶端的本機資料夾加上地址，用串流模式 | 讀、寫 |
| bot 平台 | 它的雲端硬碟連線，用檔名或資料夾名稱搜尋 | 只能讀；要存檔交給 Orca |
| Slack | 貼雲端連結會顯示預覽；PDF 也可以直接傳到相關頻道 | 看、貼連結、收 PDF；正本仍放雲端硬碟 |

什麼能放在哪：

| 層級 | 內容 | 規則 |
|---|---|---|
| **直接放** | 交付成品、媒體、研究、公開資料、規則文件 | 放到對應的專案資料夾 |
| **加密才放** | 專案機密資料、客戶資料、個資、成績、證件、財務、保險、報價和成本、沒有遠端備份的 repo | 只放加密備份組，用擁有者的公鑰加密；私鑰永遠不經 agent 的手 |
| **永遠不放** | 密碼、金鑰、token、`.env`、私鑰 | 加密也不放 |
| **不搬** | 開發中的 repo 工作目錄、`.git`、相依套件資料夾、資料庫 | 同步會弄壞它們。程式碼靠 Git 備份，雲端只放打包加密後的檔案 |

**為什麼這麼嚴：** bot 平台的雲端硬碟連線涵蓋整個帳號、所有 bot 共用，不能限定在某個資料夾，連會讀陌生人訊息的 bot 也讀得到。

**分享**預設關閉。分享檔案或開公開連結是對外動作，要走決策卡（第 20 章）。必須維持公開的既有分享資料夾留在原處不動。**把檔案搬到雲端**的步驟是：複製、核對雜湊、確認雲端有了，才刪本機；只有媒體和結案資料會刪本機。repo 附有[路徑規則模板](../../templates/zh-TW/cloud-path-rules.md)。

## 21.7 紀錄：結果一定要放到哪裡

| 類型 | 例子 | 保留 |
|---|---|---|
| 永久 | 決定、批准、對外紀錄、收據文字、規則、路由 | 永久，只增不改 |
| 日常 | 交接、回覆檔、日誌 | 留本機；30 天後壓縮，不刪 |
| 媒體 | 影片、大量截圖、模型檔 | 14 天後移到雲端硬碟的封存組（複製、核對雜湊、再刪）；不進 Git |

- **先寫短的。** 每次交接和回報都先寫短的；長內容放檔案，只傳路徑。
- **每個角色一頁。** 每個角色的規則一頁以內，重複的內容只留連結。

**結果當晚就放到團隊看得到的地方**〔規約：2026-11 起〕。一個有共用研究站的團隊專案裡，好幾週的進度只留在聊天和收據裡，擁有者問為什麼研究站沒更新。從那之後的規則：

1. 每次實際送出、每輪研究結束後，由做這件事的 writer **當晚**把摘要同步到團隊的研究站。只留在聊天訊息和收據裡，不算有記錄。
2. 寫入前先在本機備份研究站的資料；寫入後讀回新增和更新的筆數，並確認舊資料都還在。
3. 被取代的項目標成「已取代」，不要刪除。還沒出來的結果不要猜著填。候選、失敗和跳過的，絕不顯示成已送出。官方平台的結果和本機的量測分開。
4. 同步失敗就保留一份本機待補清單，並照實說。「已送出」不等於「研究站已更新」。
5. 研究站和 Slack 只放核可過的摘要；原始資料、憑證和備份都留在本機。

這是寫成文字的流程，不是已安裝的排程。

## 21.8 證據與限制

| 項目 | 參考部署的證據 | 限制 |
|---|---|---|
| 專案 CTO | 已建立數位；新增專案時測過一次 bot → CTO 的來回 | 上限與 48 小時規則都是規約；沒有東西擋得住第六位 CTO |
| 派工宣告與紀錄 | 已記錄數千筆判斷；巡檢會統計 | 只統計得到有記錄的判斷 |
| 給 writer 的補充指令 | 包裝工具的確認與 log；參考部署的離線測試 | 排進佇列還不等於開始新的一輪 |
| 每日巡檢 | 在三個時間執行；摘要模型沒有工具 | 摘要可能出錯；它只是指引，不是證據 |
| 看板同步 | 欄位與 ◆ comment 透過原生中繼資料寫入 | 看板顯示的 bug 在上游；畫面由擁有者確認 |
| 雲端路徑規則 | 2026-11 起使用；安裝桌面版後核對過同步路徑 | 加密的安全性取決於擁有者怎麼保管金鑰 |
| 當晚寫入研究站 | 定為規則，並做一次性回補；撰寫本章時沒有核對回補是否完成 | 沒有自動化 |
