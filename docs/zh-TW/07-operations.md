# 第 7 章　日常維運：巡檢、看板、checkpoint、恢復

[English](../en/07-operations.md) | [繁體中文](../zh-TW/07-operations.md) | [Home](../../README.md)

## 7.1 原則：不開無限輪詢

總控不應該自己開一個無限迴圈一直盯著所有聊天室〔規約〕。理由：耗額度、塞上下文、也可能誤送輸入。參考部署的做法是：

- **背景收集用一般程式**，不呼叫模型。
- **定時巡檢**才用一次便宜模型寫摘要，而且不給它任何工具。
- **總控只在 User 喚起、或聊天室有人類指示時**才做盤點與派工。

## 7.2 參考部署的背景服務（核實值）

以下數值於撰寫當日從參考部署的排程設定與程式碼核實，**是那台機器的設定，不是建議值**。本包不附這些服務。

| 服務 | 頻率 | 做什麼 | 會不會改東西 | 標記 |
|---|---|---|---|---|
| 收集與看板同步 | 每 60 秒 | 讀 Orca 工作區與終端清單、各站回報、來源文件修改時間；重建彙整；推送有變化的看板卡片；並維護已登記工作區的規則入口檔 | 對專案狀態來源唯讀；會寫自己的資料庫、彙整檔、看板卡片，以及（先備份）已登記工作區的規則入口檔；不啟動代理、不派工 | 〔程式・自製，系統排程〕 |
| 每日巡檢 | 每天 3 次固定時刻 | 唯讀。一般程式收集事實（等你、阻塞、近期期限、超時未回報、失效聊天室、派工判斷統計）→ 模型寫短摘要 → 寫入收據資料夾的 `LATEST.md`、更新一個「每日巡檢」任務、送一則通知 | 模型呼叫時停用所有工具；有花費上限；失敗時改用純程式摘要 | 〔程式・自製〕 |
| 機器健康檢查 | 每 30 分鐘 | 檢查交換空間、pipe 容量、磁碟剩餘、AI 相關程序數、同時開的代理聊天室數 | 只有超過門檻才通知；相同警告 3 小時內不重發 | 〔程式・自製〕 |

巡檢判定的門檻（參考部署設定檔中的值）：

- 「進行中／阻塞」的站台回報超過 72 小時未更新 → 列為超時未回報
- 期限在 3 天內 → 列為近期期限
- 站台回報超過 24 小時 → 在彙整中標為過期
- 健康：交換空間 > 12 GB、pipe 容量 < 4096 bytes、磁碟剩餘 < 25 GB、AI 相關程序（各種代理與其子程序合計）> 200、**Codex** 對話程序 > 12 → 警告。這些是那台機器的參考值，不是通用安全上限；只警告，不阻擋

為什麼要有健康檢查：同時開太多代理聊天室會把一台個人電腦的記憶體與系統資源耗盡，嚴重時整個圖形介面當掉。**經驗法則：同時活躍的代理聊天室控制在十個左右以內，做完的就關掉或讓它休眠。**〔規約〕

開工或接手前，先讀巡檢的 `LATEST.md`，比自己重新掃一遍便宜得多〔規約〕。

## 7.3 看板

Orca 的工作區看板（Workspace board）預設四欄：`todo`、`in-progress`、`in-review`、`completed`。每個工作區是一張卡，卡片有欄位與一行 comment，都可以用原生命令設定〔程式・原生〕：

```
orca worktree set --worktree active --workspace-status in-review --json
orca worktree set --worktree active --comment "測試通過，等待審查" --json
```

參考部署把助理任務狀態對應到看板欄位〔程式・自製，設定可調〕：

| 任務狀態 | 卡片欄位 | comment 標籤 |
|---|---|---|
| waiting_user | todo | ⚠等你 |
| blocked | todo | ⛔阻塞 |
| review | in-review | 待驗收 |
| working | in-progress | 進行中 |
| planned | todo | 已排程 |
| inbox | todo | 收件 |
| （User 確認完成） | completed | 由 User 手動拖入，同步不會自動移入 |

一張卡同時有多件事時，依「等你 > 阻塞 > 待驗收 > 進行中 > 已排程 > 收件」排序，只顯示最重要的一件。

comment 規則：

- 同步程式寫的 comment 以一個固定符號（參考部署用 `◆`）開頭，格式「標籤｜事項（另 N 項）｜下一步｜督導 A 或 B」。
- **聊天室自己寫的 comment 不要用這個符號開頭**，同步程式就不會覆蓋它，只會調整欄位。
- User 手動拖過的卡片，同步程式會尊重：只有該卡實際狀態又改變時才重新移動。
- 自訂欄位有已知問題時，先只用預設四欄〔未知：依你的 Orca 版本而定〕。

## 7.4 低 token checkpoint 與增量讀取

| 做法 | 怎麼做 | 標記 |
|---|---|---|
| 聊天室在檢查點寫一行卡片 comment | `orca worktree set --worktree active --comment "<一句話>"`：重現問題後、修完後、驗證後、交接時、遇到阻塞時 | 〔程式・原生〕＋何時寫〔規約〕 |
| 讀終端用游標分頁，不要整段重讀 | `orca terminal read --terminal <handle> --cursor <n> --limit 1000 --json`；依 `nextCursor` 往後讀 | 〔程式・原生〕 |
| 讀收件匣只讀未處理的 | `orca orchestration check`：回傳最舊的一批，確認（ack）後才給下一批 | 〔程式・原生〕 |
| 只拿自己的任務 | 自製 `brief` 只回傳本站身份、契約 hash、本專案未完成任務 | 〔程式・自製〕 |
| 先讀摘要再讀原始資料 | 巡檢 `LATEST.md` → 任務列表 → 必要時才讀聊天室 | 〔規約〕 |
| 完全相同的回報不重寫 | 自製 `report` 對完全相同內容視為 no-op | 〔程式・自製〕 |

## 7.5 斷線、恢復與失聯

### 什麼情況算「需要恢復」

- 聊天室顯示重連失敗、無法還原、代理迴圈結束等訊息。參考部署用工作區預覽文字比對這幾種字串來偵測〔程式・自製，啟發式〕。
- 代理已退回 shell 提示字元。
- Orca 重啟後 terminal handle 失效（出現 handle stale 類錯誤）〔程式・原生〕。

### 恢復步驟（只由維運領域督導執行）〔規約〕

模板：`templates/zh-TW/resume-recovery-checklist.md`

1. 確認該聊天室**閒置或已失效**，不是在工作中、不是 User 正在打字。
2. 先保存畫面（`orca terminal read` 的輸出存到**私人**收據資料夾，不要放進任何要分享的地方）。
3. **只用原本的 session UUID** 恢復（用該代理 CLI 自己的 resume 功能，具體旗標以你安裝版本的 `--help` 為準），保留原本的模型、推理強度、權限模式。
4. 確認同一個 UUID 沒有在別的終端也被恢復（避免兩個 writer）。
5. 恢復後重新 `orca terminal list` 取得新 handle，之後只用新 handle。
6. 在收據資料夾留下證據，通知該領域的督導。

### 不要做的事

- 不要因為「一段時間沒動靜」就判定代理死了、就重開一個。Orca 原生 orchestration 的原則是：**「沒有回應」不是「已結束」**；只有確實證明程序已退出，才能停止、放棄或重試〔程式・原生：`orca skills get orchestration` 的 Outcome 與 Authority 段落〕。
- 想暫時收起但之後要接著用的工作區，用 Orca 的休眠（Sleep），不要關閉終端；關閉會移除該工作區的終端與代理恢復紀錄〔程式・原生：`orca skills get orca-cli` 的 Terminal rules〕。
- 不要替 User 升級或重啟 Orca。

### 總控失聯

- 總控暫停或不可用時，用路由的 availability 設定標記，附預計回來時間；期間由核對者代理〔程式・自製計算代理人；代理人接手是規約〕。
- 站台超過門檻沒回報、或 Orca 不可達時，彙整一律顯示「未知／過期」，**不推定完成**〔程式・自製＋規約〕。

## 7.6 規則更新的同步

執行中的對話**不會自動重讀** AGENTS.md／CLAUDE.md。2026-10 起，任何一方修改總控規則後〔規約〕：

1. 用 `orca orchestration send --type status` 寄到另一位總控的**長駐 Run**，附變更摘要、檔案路徑與前後 hash；不再直接打字進對方的終端。
2. 對方閒置時 Orca 會自動打一行提醒；對方忙碌時不打擾，也不重複〔程式・原生〕。指令與限制見 14.7。
3. 對方 ack 並回覆「已重讀＋版本」，才算同步完成。
4. 共同契約改版時，各站台在下次 `brief` 會拿到新的 hash，讀完後重新 `join`〔程式・自製：舊 hash 無法回報〕。

## 7.8 專屬入口恢復

依[第 16 章](16-dedicated-project-intake.md)區分 pending 與 unknown；不盲目重送結果不明的投遞。沿用原收據／key，不重建需求或任務。總控 session 替換後重新核對 terminal／mailbox 綁定。Discord 預設 profile 與客戶 LINE profile 隔離；重載前檢查進行中工作、待處理 spool 與 lock，重載後驗證載入 hash、連線及無關服務仍正常。
